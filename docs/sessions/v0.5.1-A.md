## Objectif

PDFium ne tourne plus dans le processus de la fenêtre. Un plantage, une
pile dépassée ou un dessin sans fin du moteur arrêtent son processus, pas
l'application, qui dit que la page n'a pas été rendue et relance le moteur.

## Décisions déjà prises (Martin, 3 octobre 2026)

1. **Même exécutable, mode travailleur.** Le processus de rendu est
   `fyp-app` relancé avec un argument réservé (`--fyp-render-worker`), lu en
   toute première instruction de `main()`, avant tout code de Tauri, de
   WebView2 ou de plugin. Pas de second binaire : rien de plus à construire
   en développement (`cargo run -p fyp-app` suffit) ni à empaqueter. C'est
   aussi le modèle de Chrome. Le mode travailleur n'initialise rien d'autre
   que PDFium.
2. **Canal : l'entrée et la sortie standard du travailleur**, en trames
   binaires à longueur préfixée, écrites à la main, sans dépendance de
   sérialisation. Première trame : une poignée de main avec un numéro de
   version du protocole ; un numéro inconnu est un refus. La sortie
   d'erreur du travailleur va à `Stdio::null()`. Sous Windows, le
   travailleur est lancé sans fenêtre de console
   (`std::os::windows::process::CommandExt::creation_flags`,
   `CREATE_NO_WINDOW`).
3. **Le processus de la fenêtre ne fait pas confiance au travailleur.**
   Chaque longueur annoncée est comparée à un plafond avant toute
   allocation. La réponse à un rendu est un bitmap brut (largeur, hauteur,
   RGBA) : la largeur doit être celle demandée, la hauteur sous un plafond,
   la longueur égale à largeur × hauteur × 4. C'est le processus de la
   fenêtre qui encode le PNG : il ne transmet jamais à WebView2 des octets
   compressés fabriqués par un processus qui a pu être compromis.
   L'encodage pèse environ 5 % du temps de rendu en release
   (`docs/banc-rendu.md`).
4. **Le document est envoyé une fois par identifiant**, comme le cache
   actuel, et renvoyé après une relance. Le mot de passe voyage dans la
   même trame que le document : jamais en argument de ligne de commande ni
   en variable d'environnement, que d'autres processus peuvent lire.
5. **Pannes.**
   - Travailleur mort (plantage, tué) : la demande en cours échoue avec un
     message en français (« le moteur de rendu s'est arrêté ; il sera
     relancé »), et le travailleur est relancé à la demande suivante.
   - Délai par demande dépassé : le travailleur est tué, la demande
     échoue, relance comme ci-dessus.
   - Une même page (document, page) qui fait tomber le travailleur deux
     fois est refusée ensuite sans relancer le travailleur pour elle,
     jusqu'à ce qu'un autre document soit ouvert.
   - Trop de relances en peu de temps : le rendu est déclaré indisponible
     pour le reste de la session, et l'état du rendu le dit.
   - Le travailleur se termine quand son entrée standard se ferme : si la
     fenêtre disparaît, il ne lui survit pas. Fermer l'application arrête
     et attend le travailleur.
6. **Aucun composant d'interface nouveau.** Un échec passe par les chemins
   d'erreur de rendu qui existent (vignette vide avec sa raison, vue d'une
   page, barre d'état). Les messages de rendu citent les pages à partir
   de 1.
7. **`pdfium-render` reste confiné** au code du travailleur. Le protocole
   vit dans son propre module, testable sans PDFium. Le banc
   `tools/render_bench` continue de compiler et de mesurer le même code de
   dessin.
8. **ADR 0008, « Le rendu dans un processus à part »** : le protocole, ce
   que le processus de la fenêtre vérifie, les pannes et leurs réponses, et
   les limites connues (le travailleur garde les droits de l'utilisateur :
   ce n'est pas encore un bac à sable ; mémoire non bornée jusqu'à la
   session B). L'ADR 0005 renvoie à l'ADR 0008 là où elle décrit le thread
   unique.

## Questions laissées à la session

- Le découpage en modules de `render.rs` (service côté fenêtre,
  travailleur, protocole).
- Les plafonds : taille d'une trame, hauteur et nombre de pixels d'une
  image (au moins ce qu'atteint aujourd'hui une page A4 à 4096 pixels de
  large), délai par demande, nombre de relances. Chaque valeur est
  justifiée dans l'ADR.
- Comment les tests lancent un vrai travailleur : un test unitaire tourne
  dans le binaire de test, pas dans `fyp-app`, et
  `CARGO_BIN_EXE_fyp-app` n'existe que pour les tests d'intégration
  (`app/tests/`). Propose ce qu'il faut ; une cible `lib` dans `app/` est
  admise si elle est nécessaire.
- Ce que le protocole réutilise de celui du banc, sans lier l'application
  au banc.

## Critère de fin

- Un test lance le vrai travailleur, le tue au milieu d'une demande, et
  montre que la demande échoue proprement puis que la suivante réussit.
- Des tests du protocole envoient des trames hostiles (longueur énorme,
  tronquée, dimensions fausses, version inconnue, octets aléatoires) :
  chacune donne une erreur, sans panique ni allocation démesurée.
- Les tests de rendu existants passent à travers le travailleur.
- Le travailleur s'arrête quand son entrée standard se ferme (test).
- `cargo test -p fyp-app`, `clippy`, `python tools/build_ui.py`, les
  scripts de `tools/ui_smoke/` existants, et la compilation de
  `tools/render_bench` au vert.
- ADR 0008 écrit ; `app/README.md`, `docs/architecture.md` et le
  commentaire de tête de `render.rs` disent vrai ; l'entrée de backlog
  « Isoler le rendu… » réduite à ce qui reste (droits, mémoire), l'entrée
  du commentaire de tête fermée, l'entrée des pages à partir de 0 réduite
  de sa partie `render.rs`.

## Pour le testeur

- Tue le travailleur à tous les moments possibles : avant la poignée de
  main, pendant l'envoi d'un document, pendant un dessin, pendant l'envoi
  d'une image ; vérifie qu'il n'y a ni blocage, ni processus orphelin, ni
  relance en boucle.
- Fais répondre au processus de la fenêtre un faux travailleur (un script
  sous `target/agents/v0.5.1-A/` qui parle le protocole) qui ment :
  dimensions fausses, longueurs énormes, réponse à une autre demande,
  silence.
- Un fichier chiffré après une relance : le mot de passe est-il renvoyé ?
  Vérifie qu'il n'apparaît pas dans la ligne de commande du travailleur
  (Gestionnaire des tâches ou `Get-CimInstance Win32_Process`).
- Vignettes et vue d'une page en même temps pendant une relance.
- Compte les processus `fyp-app` après la fermeture de l'application.

## Pour le relecteur

- Aucune lecture du travailleur ne fait confiance à une longueur ou à une
  dimension avant de la comparer à son plafond.
- Aucun `unwrap`, `expect` ni indexation qui peut paniquer sur ce que
  renvoie le travailleur.
- Aucun chemin où un processus enfant n'est ni attendu ni tué.
- Le mode travailleur est choisi avant tout code de Tauri.
