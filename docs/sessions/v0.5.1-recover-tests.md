## 3. Défauts

### D1 — La recherche du catalogue dans les object streams est quadratique, et le compteur ne la voit pas (bloquant)

Décision 6 : le parcours se trouve dans `recover.rs`, il se corrige donc dans
la session. Il n'est pas introduit par cette session, il préexiste.

`Scan::index_object_streams` : dès que les données décodées d'un object
stream contiennent `/Catalog`, chaque objet intérieur pas encore vu est
analysé par `Parser::at(&stream.data, offset).parse_object()` sur **toutes**
les données décodées. Les offsets de l'en-tête ne sont ni triés ni
distincts (`ObjectStream::from_decoded` les accepte tels quels), si bien
que N objets peuvent pointer sur une même chaîne de L octets, lue N fois.
Ce travail n'est ni compté par `examined` ni débité du budget.

Reproduction minimale (`gen_catalog_probe.py 1048576 x.pdf`) :

```
100000000 0 obj
<< /Type /ObjStm /N <count> /First <len(en-tête)> /Length <n> >>
stream
1 0 2 0 3 0 … 66925 0 (aaaa…512 Kio…aaaa /Catalog)
endstream
endobj
```

Mesures : `fyp info` prend 36,8 s sur un fichier de 1 Mo et 326 s (plus de
cinq minutes) sur un fichier de 3 Mo ; la sonde, 2,1 s à
256 Ko, 7,6 s à 512 Ko et 36,7 s à 1 Mo, alors que `EXAMINED` reste à
6 fois la taille. L'en-tête peut aussi venir d'un flux compressé, donc
d'un fichier bien plus petit.

Correction validée sur la copie (variante VB de `variants.py`) : trier et
dédupliquer les offsets des objets intérieurs, analyser chaque offset une
seule fois, sur les données coupées à l'offset suivant, et compter
`slice.len() - offset` par `examined`. Le corpus reste identique fichier
par fichier, et la sonde passe à 0,061 s pour 3 Mo.

Test à ajouter : `crates/fyp-core/src/recover.rs`, module `tests`,
`object_stream_probed_for_a_catalog_stays_linear` (texte complet dans
`target/agents/v0.5.1-recover/testeur/proposed_test.rs`). Il construit
l'object stream ci-dessus à 64 Ko, vérifie que tous ses objets sont indexés
et que `examined <= LINEAR * file.len()`. Il n'échoue sur le code actuel
que si la recherche du catalogue est comptée sur ce que le parseur peut
lire : sans compteur, il passe (V0), avec le compteur, il échoue
(159 044 231 octets pour 65 648, VA), avec le correctif, il passe (VB). Le
fichier étant fabriqué par le test, aucune fixture n'est nécessaire.

### D2 — Les object streams sont tous décodés à l'ouverture, sans budget : une bombe de décompression par flux (à corriger)

`index_object_streams` décode chaque `/Type /ObjStm` trouvé, chacun sous la
seule limite `DecodeLimits::max_output` (256 Mio par étage). Un flux de
983 octets compressé deux fois (`/Filter [/FlateDecode /FlateDecode]`)
donne 256 Mio, soit 0,33 s de décompression. Ce travail n'est ni compté ni
débité. `gen_bombs.py 64` produit un fichier de 43 Ko que `fyp info` ouvre
en 22,6 s ; à 3 Mo (environ 5 500 flux), on peut estimer une demi-heure.
Le travail reste borné par flux, donc linéaire au sens strict, mais avec un
facteur de 270 000 par octet. Le compteur `EXAMINED` ne le voit pas, et la
borne de 64 ne dit rien de ce cas.

Correction possible dans `recover.rs` : débiter du budget du scan les
octets décodés, ou décoder sous `max_output = min(limits.max_output,
budget restant)`. À trancher par la session principale : est-ce un
« parcours non linéaire » au sens de la décision 6 ? Le chemin normal
(table déclarée) décode ses object streams à la demande, et une
arborescence de pages répartie sur des milliers de bombes l'atteindrait
aussi : ce volet sort de `recover.rs` et relève du backlog. Rien n'est
consigné à ce sujet dans `docs/backlog-technique.md`.

Test à ajouter si la correction est faite :
`recover::tests::object_stream_bombs_are_debited_from_the_budget`. Il
construit une dizaine de flux doublement compressés à une limite de
quelques Mio (`DecodeLimits { max_output: 4 << 20 }`) et vérifie que le
total décodé, compté par `examined`, reste sous `BUDGET_FACTOR` fois la
taille, ou plancher, et que les flux qui ne tiennent pas dans le budget
sont sautés.

### D3 — Deux promesses de la session ne sont tenues par aucun test (à corriger)

1. **Le débit de la décision 1 (mutant M2).** Si l'on retire
   `if !self.spend(searched) { return None; }` de `Scan::object_end`, les
   10 tests de `recover` passent encore. Le débit fait en partie double
   emploi avec l'analyse qui suit (la tranche serrée ou large couvre
   toujours les octets que la recherche a parcourus), aucun motif hostile
   ne le rend donc observable. Test à ajouter :
   `recover::tests::the_stream_search_is_debited_from_the_budget`. Il
   construit un `Scan` à la main sur `b"1 0 obj << /A 1 >> endobj"` avec un
   budget connu, appelle `object_end(7)`, et vérifie que le budget a perdu
   exactement les octets compris entre 7 et le `endobj`. Puis, avec un
   budget plus petit que ce parcours, que `object_end` renvoie `None` et
   que le budget vaut 0.
2. **Le compteur de `load_object_stream` est déclaratif (mutant M3).**
   `examined(end.saturating_sub(at))` compte la tranche que le code est
   censé lire, pas celle qu'il lit vraiment. Si l'on remet
   `let slice = self.input;` (le comportement d'avant), le compteur ne
   change pas et `object_streams_aimed_at_a_far_endstream_stay_linear`
   passe, en 39 s au lieu de 0,5 s, sans rien prouver. Correction :
   construire la tranche d'abord, puis compter
   `slice.len().saturating_sub(at)`. Avec ce compteur, le même mutant fait
   échouer le test (44 220 643 537 octets pour 3 145 650, cas 28). Le même
   principe vaut pour le compteur de D1.

### D4 — La borne `LINEAR = 64` ne tient qu'à l'écriture exacte du motif (backlog, déjà consigné en partie)

Le nouveau motif `1 0 obj << endobj ` passe à 63,16 fois la taille. Le même
objet vide écrit plus serré la dépasse : `1 0 obj<<endobj ` à 70,1,
`1 0 obj endobj ` à 74,2. Un fichier **sain**, `1 0 obj 1 endobj` répété,
la dépasse aussi, à 65,2. La cause est `on_comment_line`, qui compte
1 024 octets par candidat ; le coût reste linéaire (cas 13, 14 et 18 :
ratios constants de 64 Ko à 3 Mo). L'auteur a consigné cette cause dans
`docs/backlog-technique.md`, avec les chiffres 63, 65 et 117. J'y ajoute
seulement les écritures serrées du motif même du brief (70 et 74). Si la
ligne de backlog est reprise, le test devrait recevoir ces écritures du
motif ; sinon, le premier changement du coût par candidat cassera ce test
sans qu'aucun parcours quadratique n'y soit pour rien. Le critère de fin,
tel qu'il est écrit, est tenu.

#### D6 — Un catalogue dans lequel un autre objet est déclaré n'est plus reconnu (backlog)

Avant la session, la recherche du catalogue analysait chaque objet sur
toutes les données décodées ; elle l'analyse maintenant sur les données
coupées à l'offset suivant. Si l'en-tête déclare un autre objet à un
offset qui tombe dans les octets du catalogue (offsets qui se
chevauchent, contraires à ISO 32000-2, 7.5.7), le catalogue coupé ne
s'analyse plus, et un fichier sans trailer utilisable perd son `/Root` :
`/Root` = 1 avant, absent après (T13). La couche document, elle, lit
toujours l'objet sur toutes les données. La table reconstruite est la
même, aucun fichier du corpus n'est touché (T15) : la décision 3 tient,
telle qu'elle est écrite. C'est le prix de la linéarité ; un repli borné
reste possible (une seule analyse sur toutes les données par flux,
réservée à l'objet dont la tranche coupée contient `/Catalog` sans
s'analyser), à juger hors de cette session.

Ligne de backlog proposée (`docs/backlog-technique.md`) : « La
reconstruction ne reconnaît plus un catalogue rangé dans un object stream
quand un autre objet y est déclaré à un offset qui tombe dans ses octets
(offsets qui se chevauchent) ; avant v0.5.1-recover, elle le reconnaissait.
Aucun fichier du corpus n'est concerné. »
